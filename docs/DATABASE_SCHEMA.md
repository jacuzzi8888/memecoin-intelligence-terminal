# Database Schema

## Schema Overview

PostgreSQL 16 with Drizzle ORM. Schema designed for:
- Append-only raw data with provider provenance
- Normalized domain entities
- Versioned derived intelligence
- Efficient querying for hot paths
- JSON columns only where flexible schema is justified

## Table Groups

### Users & Configuration
```sql
users                    -- Auth.js user accounts
user_profiles            -- Display names, avatars, preferences
user_settings            -- Notification, display, trading preferences
notification_destinations -- Telegram chat IDs, Discord webhooks, emails
linked_wallets           -- User's public Solana wallet addresses
watchlists               -- User-created watchlists
watchlist_items          -- Tokens or wallets in a watchlist
```

### Tokens & Markets
```sql
tokens                   -- Canonical token records (address, symbol, name, etc.)
token_launches           -- Token creation events (deployer, time, initial liq)
markets                  -- Trading pairs / liquidity pools
token_snapshots          -- Point-in-time market metrics for tokens
market_snapshots         -- Point-in-time metrics for markets/pools
raw_provider_events      -- Raw blockchain events with provider provenance
normalised_token_events  -- Processed token lifecycle events
```

### Wallet Intelligence
```sql
wallets                  -- Canonical wallet records
wallet_labels            -- Classification labels (bot, insider, bundler, etc.)
wallet_trades            -- Normalized trade records
wallet_positions         -- Current and historical token positions
wallet_performance       -- Calculated performance metrics (PnL, win rate)
wallet_relationships     -- Funding, clustering, co-occurrence relationships
wallet_cohort_definitions -- Named cohorts of qualified wallets
wallet_cohort_members    -- Wallet membership in cohorts
```

### Scanner & Alerts
```sql
strategies               -- User or system signal strategies
strategy_versions        -- Versioned strategy configurations
signals                  -- Generated signal records
signal_factors           -- Explainable factor contributions per signal
alerts                   -- Generated alerts
alert_deliveries         -- Delivery records per channel
alert_outcomes           -- Post-alert outcome tracking
```

### Trading
```sql
trading_accounts         -- Non-custodial wallet connections
trade_intents            -- User's intended trades
quote_records            -- Retrieved swap quotes
simulated_orders         -- Simulated trade results
execution_attempts       -- Transaction submission attempts
transaction_records      -- On-chain transaction tracking
```

### System Operations
```sql
data_providers           -- Registered provider configurations
ingestion_checkpoints    -- Resume points for data ingestion
background_jobs          -- Job execution and status tracking
processing_failures      -- Failed processing records for retry
feature_versions         -- Scoring/feature calculation version registry
```

## Key Design Decisions

### Numeric Precision
- Token amounts: `NUMERIC(40, 20)` for Solana's 9-decimal lamports
- Prices: `NUMERIC(30, 15)` for precision
- Percentages: `NUMERIC(10, 4)` for basis-point accuracy
- Scores: `INTEGER` (0-100) for simplicity
- Confidence: `NUMERIC(5, 4)` for 4-decimal precision

### JSON Columns
Used only where schema flexibility is justified:
- `raw_provider_events.raw_data` -- Provider-specific response
- `signals.metadata` -- Strategy-specific signal data
- `signal_factors.details` -- Factor calculation details
- `user_settings.preferences` -- Flexible user preferences

### Indexes
- Primary keys: UUID v7 for time-ordering
- Foreign keys: Indexed on all relationships
- Query indexes: Composite indexes for common query patterns
- Partial indexes: For active/visible records only
- GIN indexes: For JSON column queries when needed

### Soft Deletes
Not used. Data is append-only or archived.
- `deleted_at` columns exist only for user-generated content
- System data is never deleted, only expired/archived

## Migration Strategy

1. Migrations are generated by Drizzle Kit
2. Migrations are applied in order by `pnpm db:migrate`
3. Never edit applied migration files
4. Schema changes create new migrations
5. Breaking changes require data migration scripts
6. All migrations are reversible where possible
